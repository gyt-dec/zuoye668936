# 阶段8：索引与大规模关联查询性能实验计划

## 1. 目标与边界

阶段8复用阶段7已经建立的固定大数据集，比较新增普通联合索引前后的查询执行计划、重复执行时间、写入代价和索引空间。实验不删除、清理或重建P7数据，不修改阶段3—7业务代码，不进行并发实验。

## 2. 前置基线

- OceanBase CE 5.0.1.0、MySQL兼容模式、`phone_recharge_db`；
- 7张业务表、P4基准、阶段5的2个视图和2个触发器、P6无残留；
- P7数量分别为100000、100000、100000、100000、100000、120000、100000；
- 首次执行时不存在名称以`idx_p8_`开头的性能索引。

程序从`information_schema.STATISTICS`读取实际索引。不存在阶段8索引时执行完整前后对比；三个索引全部存在且定义完全正确时，只允许使用已保存的无索引基线恢复后半段；部分存在、定义错误或缺失基线文件均立即停止。

## 3. 查询和索引

| 查询 | 业务含义 | 新增索引 |
|---|---|---|
| Q1 | 指定时间范围内未使用卡的数量与金额 | `recharge_card(card_status, created_at, card_id)` |
| Q2 | 指定时间范围内充值记录关联手机号、机主和卡 | `recharge_record(recharged_at, mobile_id, card_id)` |
| Q3 | 已完成订单关联用户、明细和充值卡 | `purchase_order(order_status, created_at, user_id, order_id)` |

索引只包含过滤、连接或稳定定位所需字段，不重复创建主键和业务唯一索引。正式DDL见`sql/30_phase8_create_performance_indexes.sql`。

## 4. 测量方法

每个查询先预热1次，再连续执行5次，保存每次毫秒数并以中位数比较，减少单次抖动。索引前后使用完全相同的SQL、参数和数据，结果集合必须一致。每个阶段保存`EXPLAIN`原始行，不凭计时结果推测执行计划。

写入代价使用每轮200张带`P8-PERF`标记的临时充值卡，共重复5轮；每轮都在事务中写入并立即回滚。最终必须验证P8残留为0。AUTO_INCREMENT可能产生编号空洞，这是MySQL兼容数据库回滚自增写入的正常现象，不影响业务数据。

`information_schema.TABLES.INDEX_LENGTH`用于记录索引空间变化；若OceanBase版本返回0或近似值，按真实值记录并在分析中说明限制，不伪造空间占用。

## 5. 自动化与结果

唯一入口：

```bash
bash scripts/run_phase8_index_performance.sh
```

输出包括无密码文本日志、JSON明细和CSV对比表。PASS表示环境和数据基线正确、索引定义正确、查询结果一致、EXPLAIN和计时完整、临时写入无残留；不要求所有查询都必须变快，变慢或差异不明显也作为真实实验结果分析。

## 6. B+树与Hash理论安排

OceanBase实际实验只使用当前版本真实支持的普通索引，不假设存在`CREATE HASH INDEX`。B+树适合范围查询和有序扫描；Hash索引适合等值查找但不擅长范围与排序。阶段8取得执行计划后再结合真实索引行为完成理论分析，自行实现B+树则留在算法阶段。
