# 阶段7：10万级关联数据与Python批量插入计划

## 1. 阶段目标与边界

本阶段只建立稳定、可校验、可恢复的大规模业务数据集，为阶段8索引和复杂JOIN性能对比提供固定基线。本阶段不创建性能索引，不比较查询耗时，不运行并发实验，也不修改阶段5的视图和触发器。

计划单一入口：

```bash
bash scripts/run_phase7_large_data.sh
```

入口及Python生成程序已经实现并完成云端代码级检查，尚未连接或修改本地OceanBase，当前状态为“待ChatGPT审核、待本地执行”。

## 2. 数据规模

使用统一的`P7`标记，目标如下：

| 表 | P7目标行数 | 标记或识别方式 |
|---|---:|---|
| `app_user` | 100,000 | `login_name`为`p7_user_00000001`起 |
| `owner` | 100,000 | `owner_name`为`P7_OWNER_00000001`起 |
| `mobile_number` | 100,000 | 独立的P7号码段，并通过P7 owner外键复核 |
| `purchase_order` | 100,000 | `order_no`为`P7-ORDER-00000001`起 |
| `order_item` | 100,000 | 通过P7订单外键识别 |
| `recharge_card` | 120,000 | `card_no`为`P7-CARD-00000001`起 |
| `recharge_record` | 100,000 | 通过P7充值卡外键识别 |

七张相关表均达到10万级。前20,000个订单各购买2张卡，其余订单各购买1张，共120,000张卡；其中100,000张形成充值记录并由阶段5触发器变为`USED`，保留20,000张`UNUSED`卡供后续索引和并发实验。

100,000个订单与100,000条订单明细严格一一对应。每个订单只有一个面额明细；订单总额等于`denomination × quantity`，该明细下每张卡的`face_value`等于`denomination`。100,000条充值记录与100,000张USED卡一一对应，另外20,000张UNUSED卡没有充值记录且`used_at`为空。

第i个`app_user`与第i个`owner`用于模拟同一序号下的购买者与机主，但二者仍是独立实体，数据库中不增加没有原始需求依据的直接外键。

面额按10、20、30、50、100元循环，时间按可重复规则分布到多个日期和时段，手机号、订单号、卡号均由序号确定。生成器不使用随机值作为主标识，保证失败后可以判断完整前缀并继续。

## 3. 批量生成与插入顺序

严格按外键顺序插入：

1. `app_user`；
2. `owner`；
3. `mobile_number`；
4. `purchase_order`；
5. `order_item`；
6. `recharge_card`；
7. `recharge_record`。

Python使用PyMySQL参数化`executemany()`，默认每批500行。每一批是独立事务：成功后提交，失败则只回滚当前批次并停止。不会关闭外键、CHECK或触发器，不使用`LOAD DATA`绕过业务规则。

父表主键不假定连续。生成子表批次前，程序按P7业务键查询父表主键并建立本批映射，避免依赖`AUTO_INCREMENT`连续性。充值记录插入时继续保留阶段5触发器，让卡状态和`used_at`由已验证的数据库逻辑维护。

固定密码摘要可以复用一个符合项目摘要格式的P7测试摘要，以减少客户端CPU开销；摘要只用于生成数据，不记录真实数据库密码或可用于登录的明文。

## 4. 低资源环境控制

`coursework`租户约2 GiB内存，采用以下限制：

- 默认批次500行，允许在脚本内部配置为200至1000，不允许一次提交10万行；
- 只保留一个批次和必要的父键映射，不把完整720,000行对象同时放入内存；
- 每批提交后释放参数列表，并周期性输出进度；
- 单线程写入，避免批量生成阶段与后续并发实验混在一起；
- 运行前记录当前业务库表大小和WSL文件系统剩余空间；空间不足时停止，不自动扩容或修改OceanBase资源参数；
- 通过`GV$OB_SERVERS`读取`DATA_DISK_IN_USE`和`LOG_DISK_IN_USE`；当前租户无法取得真实使用量或版本缺少字段时直接停止，不能用配额或估算值冒充；
- 不修改`memory_limit`、租户内存、日志盘或隐藏参数；
- 分批提交控制单事务日志量，降低4 GiB租户日志盘被长事务占满的风险。
- 1000组预实验前后分别记录OceanBase数据/日志盘和WSL文件系统空间；按实际数据增长的1.5倍保守外推剩余数据需求，数据盘及文件系统均预留2 GiB，日志盘不做线性外推但始终保留1 GiB；每20个批次重新检查资源。

真实插入耗时、每批耗时和最终数据库大小只能由本地执行日志记录，设计文档不预填数值。

## 5. 重复执行与恢复

程序启动时分别统计七张表的P7行数，并校验每张表的序号是否构成从1开始的完整前缀：

- 全部为0：从头开始；
- 存在合法完整前缀：从该表下一序号继续；
- 出现空洞、重复业务序号、子表多于父表或金额/状态不一致：立即FAIL，不盲目续跑；
- 已达到目标：进入只读复核，不重复插入。

恢复以数据库中的已提交数据为准，不只依赖本地checkpoint文件。这样即使进程在“数据库提交成功、文件尚未更新”之间中断，也不会重复写入。

清理作为显式维护模式设计：

```bash
bash scripts/run_phase7_large_data.sh --cleanup
```

清理前必须再次输入明确确认文本，只删除P7标记数据，按`recharge_record`到`app_user`的反向外键顺序分批删除。默认入口绝不自动清理，不使用`DROP`、`TRUNCATE`或关闭外键。清理模式将在实现后单独做静态和模拟审核，不能与正常生成误触发。

## 6. 前置与后置保护

运行前必须验证：

- OceanBase版本、MYSQL兼容模式和`phone_recharge_db`；
- 7张业务表存在；
- P4基准为`10,10,11,10,11,11,10`；
- P5视图/触发器为`2,2`；
- P6残留为0；
- 当前没有阶段8性能索引；
- P7现状满足“空集或可恢复完整前缀”。

运行后必须验证：

- 七张表P7行数达到目标；
- 六类外键孤儿计数全部为0；
- 订单金额、明细数量、卡面额、充值金额、卡状态及`used_at`一致；
- `recharge_record.card_id`没有重复；
- P7 USED卡为100,000、UNUSED卡为20,000；
- P4基准、P5对象和P6残留保持不变；
- 两个阶段5视图能查询P7数据；
- 购卡明细视图P7行数为120,000，充值历史视图P7行数为100,000；
- 保存每表插入数量、批次数、真实耗时及最终校验结果。

## 7. 为阶段8预留的查询

阶段7只确认查询结果正确并记录数据分布，不做索引前后计时。阶段8可复用：

1. 按手机号和时间范围查询充值历史；
2. 用户—订单—明细—充值卡四表JOIN，按状态和面额统计；
3. 机主—手机号—充值记录—充值卡四表JOIN，按日期和面额聚合；
4. 按`card_status + created_at`筛选未使用卡；
5. 按时间范围、手机号或订单号进行有选择性的查询。

候选普通索引和联合索引只在阶段8创建。阶段7保留当前约束索引状态，先建立无额外性能索引的数据基线。

运行前读取`information_schema.STATISTICS`，只允许既有PK、UNIQUE和外键支撑索引；发现额外性能索引立即停止，避免破坏阶段8的无索引基线。
